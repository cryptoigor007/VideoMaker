# CP29 — глубокий аудит ошибок, мёртвого кода и рисков восстановления

**Базовая точка:** полный архив `VideoMaker_FULL_R57_CP28_FINAL_AUDITED.zip`  
**SHA-256 исходного ZIP:** `eaaccf9a58dfac1b6cfa5d12deb4c04226e5693d9411d4533cbd02feff2a341a`  
**Назначение CP29:** аудит и воспроизводимые сценарии. Файлы production-кода намеренно не изменены: исправления остаются отдельной задачей, как просил пользователь.

## Краткий вывод

Базовая регрессия остаётся зелёной, но она **не доказывает готовность приложения к безошибочной эксплуатации**. Аудит выявил несколько воспроизводимых ошибок в API, очереди, checkpoint и запуске. Самые рискованные: API может отвечать, даже когда объявлено выключенным; очередь способна пометить неготовый выпуск как `done`; checkpoint может пропустить транскрипцию/анализ после ошибки сохранения; запрос, которому API уже вернул timeout, может исполниться позже; настройки модели Whisper показывают значения, которые движок не применяет.

## Подтверждённые функциональные дефекты — исправлять в первую очередь

### CP29-01 · P1 · API «выключен», но сокет всё равно открывается

**Файлы:** `video_maker/api/server.py:180–201`, `check_key()` около 230+, `start_api()` в `video_maker/api/__init__.py`.  
`start_api()` проверяет `enabled`, но сам `VideoMakerAPI.start()` — нет. Повторный запуск сервера после `do_config_set({"enabled": false})` тоже вызывает этот метод. В результате порт продолжает слушать; публичные маршруты `/`, `/embed`, `/api/health`, `/api/openapi.json` продолжают отвечать. При `lan=true` сервер остаётся привязан к `0.0.0.0`, хотя пользователь только что отключил API.

**Воспроизведено:** `enabled=false` → `start()` вернул URL; локальный `/api/health` ответил HTTP 200; listener жив.  
**Исправление:** сделать `enabled` предусловием самого `start()`; при отключении закрыть сокет и вернуть `None`/явное состояние; добавить HTTP-тест, подтверждающий отсутствие listener, включая старый `lan=true`.

### CP29-02 · P1 · Очередь маркирует выпуск `done`, даже если нет видео

**Файлы:** `video_maker/api/control.py:252–325` (`find_series_dir/find_results`), `video_maker/api/queue.py:267–280` (`_finish`), `video_maker/pipeline/finalize.py:497`, `654–678`.  
`find_results()` устанавливает `ready = bool(series_dir)`, а папка серии распознаётся по `info_metadata.txt`. `_finish()` проверяет только `result.ready` и `result.total_bytes`. При этом `FinalizeStage` создаёт `info_metadata.txt` и отчёты **до** fail-closed проверок BGM/отсутствующих Shorts и только потом может бросить `RuntimeError`. Тогда папка и байты есть, но нужных MP4 может не быть — очередь всё равно ставит `DONE`, а webhook уведомит об успехе.

**Воспроизведено:** в папке серии только `info_metadata.txt` (18 байт), MP4-файлов 0; `find_results()` вернул `ready=true`, `total_bytes=18`.  
**Исправление:** использовать финальный success-sentinel/manifest, создаваемый только после всех проверок; проверять наличие, размер и decode обязательных итоговых MP4; не использовать наличие метаданных как критерий успеха очереди и `/api/results`.

### CP29-03 · P1 · `/api/run` отвечает `started=true`, хотя приложение не запустилось

**Файл:** `video_maker/api/server.py`, `VideoMakerAPI.do_run()` около 228–280.  
После `start_pipeline()` метод ждёт фиксированные 0,4 секунды и возвращает HTTP 200 с `started=true`, но не проверяет `status.running` и факт принятия задания. `_start()` GUI может нормально вернуться без старта, если обнаружит отсутствующие/невалидные ассеты после первичной `Settings.validate()`.

**Воспроизведено:** app с валидатором без ошибок и `_start()`-заглушкой, которая ничего не запускает → ответ `200`, `started=true`, `status.running=false`.  
**Исправление:** возвращать идентификатор принятой задачи и её реальный state; после вызова проверять переход состояния или событие «started»; ранний отказ GUI должен передавать структуру ошибки обратно вызывающему API.

### CP29-04 · P1 · Ошибка записи транскрипции не инвалидирует завершённые стадии

**Файл:** `video_maker/pipeline/checkpoint.py:84–99, 126–127, 196–224`.  
Если запись `checkpoint_transcription.json` падает, код логирует ошибку и ставит `transcription_file=""`, но оставляет `TranscribeStage` (и уже отмеченный `GeminiStage`) в `completed_stages`. На восстановлении ветка очистки не срабатывает, потому что проверяется truthy `data.get("transcription_file")`; pipeline может перескочить транскрипцию и анализ с пустым `ctx.transcription`/`ctx.analysis`.

**Воспроизведено fault injection:** искусственная ошибка `OSError("simulated disk full")` при сохранении JSON оставила обе стадии завершёнными; после восстановления транскрипция `{}`, следующая стадия `MasterBuilder`.  
**Исправление:** если обязательный stage artifact не сохранён — не записывать соответствующую стадию как completed и сбрасывать все зависимые последующие стадии; лучше сделать единый атомарный commit-манифест с обязательными checksum/путями.

### CP29-05 · P1 · Checkpoint не учитывает большинство настроек и изменение исходника

**Файлы:** `video_maker/gui/app.py:2284–2291`, `video_maker/pipeline/checkpoint.py:102–128, 178–195`.  
При возобновлении проверяется точное совпадение строки `audio_path`; checkpoint сохраняет/сравнивает только флаг `voice_enhance_requested`. Не сохранены fingerprint содержимого исходного аудио и настройки, меняющие производные результаты: `remove_long_pauses`, модель/язык Whisper, модель Gemini и prompt, стили хуков/субтитров, переключатели H/V/Shorts, B-roll и их состав/mtime, BGM-платформы/источники, упаковка/обложки. Изменение этих значений не инвалидирует зависимые стадии.

**Воспроизведено:** восстановление при `remove_long_pauses=true`, когда checkpoint не содержит этого параметра, сохранило `TranscribeStage` и `GeminiStage` как completed.  
**Исправление:** versioned fingerprint по source stat/hash и только stage-relevant параметрам; граф зависимости параметров от стадий; при несовпадении инвалидировать правильную стадию и все downstream stages. Не хешировать большие B-roll файлы на каждом старте без необходимости — можно использовать инвентарь `path,size,mtime_ns` + опциональный строгий hash.

### CP29-06 · P1 · TkBridge выполняет действие после того, как запросу уже вернули timeout

**Файл:** `video_maker/api/bridge.py:70–80`.  
`call()` помещает callback в очередь и ждёт событие. По тайм-ауту вызывающий получает `TimeoutError`, но queued callback не удаляется и не помечается отменённым. Позднее `_pump()` его всё равно исполнит. Для `/api/run`/очереди это может означать: клиент увидел ошибку/перезапустил задачу, а первый callback позднее всё же запускает рендер.

**Воспроизведено:** fake Tk root не запускал pump до истечения `timeout=0.01`; `call()` выбросил `TimeoutError`, затем ручной запуск `_pump()` всё равно исполнил callback.  
**Исправление:** task envelope со статусами `queued/running/cancelled/done`; при timeout отменять только задачу, которая ещё не начала исполняться, а если уже исполняется — возвращать отдельный статус «результат неизвестен/операция выполняется» и idempotency key. Не сообщать обычный timeout, подразумевающий отказ.

### CP29-07 · P1 · Пустой/непригодный вертикальный B-roll проходит preflight

**Файлы:** `video_maker/config/settings.py:257–258, 300–318`; `video_maker/gui/app.py:2053–2068`; `video_maker/pipeline/master.py:27–40`; `video_maker/pipeline/branches.py:163+`.  
`Settings.validate()` проверяет, что заданная папка вертикального B-roll существует, но не проверяет наличие читаемых вертикальных клипов. GUI получает `bv`, только пишет число в лог и не запрещает запуск при `len(bv)==0`. `MasterBuilder` при существующей пустой папке откладывает VSTACK; фон не задан — вертикальная ветвь всё равно попытается финализировать пустой `master_vertical`. Поэтому после транскрипции, Gemini и горизонтального мастера выпуск может упасть на вертикальном результате.

**Воспроизведено:** `Settings.validate()` вернул `[]` с существующей пустой вертикальной папкой при включённой вертикальной обработке.  
**Исправление:** до запуска проверить пригодность клипов: наличие файлов, успешный ffprobe, геометрию/длительность; проверить вертикальную ветвь и все активные выходы. Либо разрешить явно отключать вертикальный результат и не запускать `FinalVertical`/Shorts, когда он не нужен.

## Дополнительные подтверждённые ошибки — P2

### CP29-08 · P2 · Нестрогие булевы API-параметры меняют смысл

**Файл:** `video_maker/api/control.py:145–210`; `video_maker/api/server.py:438–455, 724–728`.  
`apply_settings()` преобразует любую непустую строку в `True` для поля `bool`; для `remove_long_pauses: "false"` настройка становится `True`, а Tk BooleanVar получает строку `"false"` — модель и виджет расходятся. `queue.pause(bool(body.get("paused")))` и `allow_duplicate=bool(...)` имеют аналогичный риск: строка `"false"` — truthy.

**Воспроизведено:** `apply_settings(...,{"remove_long_pauses":"false"})` вернул поле в `applied`, Settings=True, GUI var=`"false"`.  
**Исправление:** schema-driven валидация типов для каждого входного поля; принимать JSON booleans как bool, остальные типы отклонять HTTP 400 вместо тихого coercion.

### CP29-09 · P2 · Неудачная смена порта навсегда гасит старый API

**Файл:** `video_maker/api/server.py:321–350`.  
`do_config_set()` мутирует и сохраняет конфиг, затем останавливает старый сервер, и только потом пробует bind нового порта. Если порт занят, вернёт 500, но старый listener уже закрыт, а `self.conf` хранит неработающий порт.

**Воспроизведено:** занятой новый порт → HTTP 500; старый порт уже не отвечает; конфиг уже указывает на занятый порт.  
**Исправление:** создать/bind новый server до публикации изменения или откатить config и восстановить старый listener, если bind провалился. Конфигурацию записывать после успешного bind.

### CP29-10 · P2 · Повреждённый JSON с неправильным корнем может сорвать запуск API/очереди

**Файлы:** `video_maker/api/server.py:111–116`; `video_maker/api/queue.py:319–349`.  
API config ожидает dict, но `conf.update(json.load(fh) or {})` ловит только `OSError, ValueError`. При валидном JSON-числе `1` `dict.update()` выбрасывает `TypeError`, который не перехватывается. Аналогично queue `_load()` может делать `for it in 1` и сорвать создание `SeriesQueue`.

**Воспроизведено:** config с содержимым `1` → `load_config()` выбросил `TypeError: 'int' object is not iterable`; queue с `1` выбросила такую же ошибку.  
**Исправление:** проверять корневой тип и обязательные поля до использования; при повреждённом config/queue делать безопасный fallback/backup файла и не оставлять приложение без API без ясного сообщения.

### CP29-11 · P2 · Whisper UI содержит неработающие настройки модели/устройства

**Файлы:** `video_maker/gui/app.py:739–742, 1510–1519, 1943–1947`; `video_maker/engines/transcription.py:24–26, 68–77, 81–84, 120–127`; `video_maker/config/settings.py:297–298`.  
GUI позволяет выбрать `tiny/base/small/medium/large-v2/large-v3/large-v3-turbo`, `cpu/cuda/auto` и `int8/float16/float32`. Но `transcribe()` жёстко вызывает `mlx_whisper.transcribe(... path_or_hf_repo=MLX_REPO)` с константой `whisper-large-v3-turbo`, не передаёт `device` и `compute_type`, а `whisperx_path` игнорируется. Cache key тоже использует `MLX_REPO`, не выбранную модель. GUI может показывать `large-v3`, но реально запускать turbo.

**Исправление:** либо честно удалить/задизейблить неподдерживаемые контролы и статус поиска WhisperX, либо поддержать модель, которую реально допускает MLX, и убрать неподходящие параметры `cuda/int8` для MLX. Логировать effective model/device, cache key должен отражать фактическую конфигурацию.

### CP29-12 · P2 · Закрытие GUI сразу завершает процесс, не дожидаясь checkpoint

**Файл:** `video_maker/gui/app.py:265–337`.  
При закрытии во время работы окно ставит cancel, убивает дочерние FFmpeg/ffprobe, затем делает `root.destroy()` и `os._exit(0)` без join рабочего потока и подтверждения сохранения checkpoint. Если закрыть окно во время транскрипции/Gemini/стадии, промежуточное состояние может не сохраниться; процесс при этом завершится с нулевым кодом, как будто всё прошло штатно.

**Исправление:** graceful shutdown protocol: попросить отмену, завершить/прервать текущую стадию, дождаться записи checkpoint и завершения worker/API/queue, затем закрывать Tk обычным выходом. Прямой `os._exit` оставить только для аварийного watchdog с явным предупреждением.

### CP29-13 · P2 · Метаданные/отчёт создаются до окончательного решения об успешном выпуске

**Файл:** `video_maker/pipeline/finalize.py:497–510, 654–678`.  
Даже помимо критерия очереди, `info_metadata.txt`, `shorts_dedup_report.json`, `bgm_report.json` и checklist остаются после RuntimeError. Это полезно для диагностики, но внешний потребитель может ошибочно принять сам факт этих файлов за успех. Нужен явный статус `incomplete/failed` или success sentinel, а не эвристика по файлам.

### CP29-14 · P2 · Нет транзакционного отката при изменении конфигурации API

Это продолжение CP29-09, но относится к любым изменяемым полям `port/lan/enabled`: значения мутабельны до подтверждения нового listener. Изменение нескольких полей может частично примениться. Объединять с исправлением CP29-09 через транзакционную конфигурацию.

### CP29-15 · P2 · Нет проверки writable/free space до дорогостоящих стадий

**Файл:** `video_maker/config/settings.py:238–262`.  
Проверяется лишь существование `output_folder`, но не запись тестового файла, свободное пространство и доступность целевого тома. Ошибка прав/переполнения может возникнуть после транскрипции/Gemini/части рендера. Добавить безвредный write-test при preflight и ориентировочную оценку места с предупреждением; не использовать жёсткий порог по размеру одного входного аудио.

### CP29-16 · P2 · Нет межпроцессной блокировки одной серии/очереди

**Файлы:** `video_maker/api/queue.py:308–317`; `video_maker/gui/app.py` при инициализации/запуске.  
Очередь использует один путь `queue.json.tmp` и атомарный `os.replace`, но межпроцессного lock нет. Два экземпляра приложения могут одновременно менять очередь и работать с одинаковыми `_vm_checkpoint.json`, `_tmp` и выходными именами. Это ограничение уже отмечалось в `VERSION.md` для CP20, но не закрыто.

**Исправление:** process singleton lock для `~/video_maker/` и output-series lock для одного `output_folder/series`; lock должен иметь PID/hostname, корректно снимать stale lock и быть тестируемым.

### CP29-17 · P3 · Секретный конфиг получает chmod только после replace

**Файл:** `video_maker/api/server.py:136–146`.  
Сначала создаётся `api.json.tmp` с правами по умолчанию, затем файл заменяет `api.json`, и лишь после этого вызывается `chmod(0600)`. На многопользовательской системе есть короткое окно, когда файл с токеном может иметь более широкие права. Задавать 0600 при создании временного файла до записи/replace.
